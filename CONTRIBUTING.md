# Contributing

Thank you for considering a contribution. This file says how to set the
project up, what a good change looks like and which rules the repository's
CI enforces and why. Everything in
the repository — code, comments, commit messages, documentation, issues and
pull requests — is in English.

Uptime Orchestrator is developed by a small team. Bug reports with a
reproduction, documentation fixes and small, well-scoped pull requests are
the most useful contributions and are reviewed first. A larger change —
a new block, a new command, a schema change, anything that touches the
agent–platform contract — should start as an issue so that the design is
agreed before the code is written; a large pull request that arrives without
one may wait, or be declined with the reasoning. We would rather say so here
than leave a pull request open for months.

## Where to file issues

- **Bugs, feature requests and questions**: the
  [issues of this repository](https://github.com/uptime-lab/orchestrator/issues).
- **Security problems**: never in a public issue. Follow
  [`SECURITY.md`](SECURITY.md).

A useful bug report names the area (UI, server, agent, provisioning,
playbooks, netboot), what you did, what you expected, what happened instead,
and — for a device issue — the agent version and the board model. Logs and
screenshots help; strip anything you would not want public first (see
[Publishing discipline](#publishing-discipline)).

## Development setup

Prerequisites: Go (the version in each module's `go.mod`), Node 22 or later
with pnpm 9 (`npx pnpm@9`), Docker (for the development PostgreSQL),
`protoc` (only when editing the protocol), and `golangci-lint` for
`make backend/lint` / `make agent/lint`.

```bash
make help                  # every target, per module

make db/up                 # PostgreSQL in Docker for local development
make db/shell              # psql into it

mkdir -p config_local && cp config/config.yaml.example config_local/config.yaml
                           # gitignored; the server reads it by default — set ports and the DSN
make backend/run           # HTTP API + gRPC server from ./cmd/server
make agent/run             # an agent process against the local server

make test                  # Go unit tests: backend, agent, tools/entitlement-signer
make test/integration      # the DSN-gated tests against the Docker Postgres;
                           # under plain `make test` they SKIP

make backend/lint          # golangci-lint
make backend/fmt

make proto/tools           # protoc-gen-go + protoc-gen-go-grpc (pinned versions)
make proto/generate        # regenerate the gRPC code AND copy it into agent/ and backend/

make backend/tools         # the swagger generator
make backend/docs          # regenerate the API documentation (mandatory after a handler change)

make agent/deb-arm         # a snapshot .deb for arm64 via GoReleaser
make eeprom/test           # the signer's input-validation tests (Python unittest)
```

Frontend, inside `frontend/`: `pnpm i`, `pnpm run dev`, `pnpm run build`,
`pnpm run lint` (max warnings 0), `pnpm run typecheck`, `pnpm run test`.
The build is `tsc -b && vite build` — the typecheck runs first on purpose,
because the committed route tree is regenerated by the Vite plugin after it.

There is no full-stack local environment with real devices; the agent and
server unit suites run anywhere, and an agent can be run against a local
server on the same machine. Hardware-dependent behaviour (netboot, EEPROM,
disk operations) is covered by tests with fakes and by the maintainers' lab;
say in the pull request what you could and could not exercise.

## Conventions

- **Go**: Clean/Hexagonal architecture, CQRS in the backend. Read
  [`docs/CODE-STYLE.md`](docs/CODE-STYLE.md) before writing Go.
  Dependency injection through constructors, named port interfaces, errors
  wrapped with `%w` and checked with `errors.Is`/`errors.As`; a refusal that
  the API should answer with its own status implements the typed-error
  interface rather than adding a per-handler branch.
- **API changes** need Swagger annotations on the handler and
  `make backend/docs`; a test fails the build when a registered route is
  undocumented or a documented route is not served. The Postman collections
  in `postman/` are kept in step by hand.
- **Protocol changes** are one commit touching `proto/`, `agent/` and
  `backend/` together, after `make proto/generate`; CI fails when the three
  generated copies differ or the generator versions drift from the pins.
- **Frontend**: typed i18n keys (`tsc` fails on a key that does not exist),
  `pnpm run lint` and `pnpm run typecheck` clean.
- **Tests** accompany behaviour changes, and a new test is run against the
  unfixed code once — a test that never failed proves nothing.
- **Documentation is part of done.** A change that falsifies a sentence in
  `docs/` or a README fixes it in the same pull request. Grep for the
  property you changed, not for the file you edited.
- **User-facing copy** follows `docs/COPY-STYLE.md`.

### Comments state the property and the reason

A comment in this tree says what must hold and why, so that the next person
can tell a deliberate shape from an accident: *"the receive runs on its own
goroutine because `stream.Recv` observes no context, so cancelling one never
unblocks it"*. It does not narrate what the code does line by line, and it
does not carry the history of how the rule was learned — no incident dates,
no finding numbers, no "measured on" notes. A rule that is worth a comment is
worth a test next to it.

## Branches, commits and pull requests

- One branch per change, from `main`; pull requests target `main` and are
  squash-merged, so the pull request title and description become the
  commit message — write them as one.
- Commit messages say what changed and why, in English, present tense,
  with the subsystem first when it helps (`agent: …`, `backend: …`,
  `frontend: …`, `docs: …`).
- **AI assistance is welcome.** You are the author of what you submit: you
  have read the change, you understand it and you can defend it in review.
  A pull request whose author cannot explain it is closed. If a tool says
  its output matches public code, treat it as
  [third-party material](#third-party-material) or remove it.
- A first pull request from a new contributor does not run CI until a
  maintainer approves the run (a GitHub setting, not a judgement about you).
  Expect that step; it is usually quick.
- Review is a conversation. A maintainer may ask for a smaller scope, a test,
  or a different shape; "no, because …" is also an outcome, and it is
  written down so that the next person does not re-propose the same thing.

## Publishing discipline

Everything in this repository is public history: commits, branch names, tag
annotations, pull-request and issue text, review comments, screenshots,
Actions logs and test output pasted from a developer machine. Nothing from a
live install goes into any of them:

- no device serial, MAC or hostname, no IP address of a real network, no
  tenant, account, person or e-mail address, no key id;
- no deploy state — which commit runs where, what was rolled back, what is
  pending;
- no description of a vulnerability that is not yet fixed and disclosed (see
  [`SECURITY.md`](SECURITY.md)).

Test fixtures use synthetic identities: example domains, documentation IP
ranges, obviously fake serials. If a real value is needed to reproduce a bug,
replace it with a placeholder in the report and share the real one through a
private channel.

Two checks enforce the part a machine can see. The **publication guard**
(`tools/publication-guard/`) runs in its own workflow, `guard.yml`, which
carries **no path filter**: every pull request, including one from a fork
and one that touches only Markdown, `docs/` or `postman/`, runs it, with no
secrets. (The test workflow, `ci.yml`, is path-filtered and skips a
documentation-only change; the guard is kept out of it for exactly that
reason, since prose is where an identifier lands.) It flags identifier
*shapes* — serial-like
tokens, private addresses, vendor MAC prefixes, home directories, mailboxes
outside the example domains, internal hostnames, the phrasing of a private
engineering journal — plus oversized and binary files. One more required
check, `private-identifier-guard`, runs only in the merge queue and on push to
`main`, because its inputs are secrets a fork cannot read; you cannot run it
locally, and it can still block a merge after the public guard passes. A
clean guard is necessary, not sufficient; the human reading of a pull request
is the rest.

Run the guard locally before pushing:

```bash
# the whole tree
python3 tools/publication-guard/check_public_shape.py --tree .

# only your new commits, and their messages
python3 tools/publication-guard/check_public_shape.py --range origin/main..HEAD

# the staged diff, for a pre-commit hook
python3 tools/publication-guard/check_public_shape.py --staged

# the other CI contracts
bash tools/publication-guard/check_proto_copies.sh
bash tools/publication-guard/check_trust_stores.sh
python3 tools/publication-guard/check_doc_citations.py --root .
python3 tools/publication-guard/check_licence_boundary.py --root .
python3 tools/publication-guard/check_workflows.py .github/workflows
```

A documented false positive is silenced on its own line with
`publication-guard: allow <rule>` and a reason beside it; every opt-out is
listed in the run summary for the reviewer. `tools/publication-guard/README.md`
describes each rule.

## What CI runs

Two repository variables govern every workflow. **`PUBLIC_CI_ENABLED`**
must be `true` for any job to run at all — unset, every job is skipped, so a
fork's Actions tab stays empty until its owner sets it. **`PUBLIC_CI_RUNS_ON`**
is a JSON array of runner labels; unset, every job runs on the GitHub-hosted
`ubuntu-24.04` runner. The platform release builds each architecture
natively, so its two build jobs read `PUBLIC_CI_RUNS_ON_AMD64` and
`PUBLIC_CI_RUNS_ON_ARM64` the same way (unset: `ubuntu-24.04` and
`ubuntu-24.04-arm`). A runner named that way gets no `sudo` from a job: the
two signer scans in `security.yml` need `gcc`, `pkg-config` and
`libpcsclite-dev` already installed there. With the defaults a pull request
from a fork executes nowhere near any machine of ours, and no job that runs
on a pull request has
a secret. No workflow may name a self-hosted runner literally or use
`pull_request_target` or `workflow_run`; a check asserts that.

`ci.yml` carries a `paths-ignore` filter (`**/*.md`, `docs/**`):
a change touching only those runs no test job. `postman/` is not in it: a
test holds every collection request to a real route. `guard.yml` carries no filter
and runs on every push to `main`, every pull request and every merge-queue
run.

| Workflow / job | What it checks |
|---|---|
| `ci.yml` → `backend` | `go vet`, `go test ./...`; the database-gated tests of every package that has one, against a real PostgreSQL service (a skip is a failure); no `gorm.Save` in the repository layer; the cross-tree guards (frontend any-scope reads match the backend's authz table; every Postman request names a served route); build, vet and tests of `tools/entitlement-signer` |
| `ci.yml` → `agent` | `go vet`, `go test ./...` for the agent module |
| `ci.yml` → `eeprom-signer` | the signer's input-validation and injection tests |
| `ci.yml` → `frontend` | `pnpm install --frozen-lockfile`, typecheck, build, unit tests, lint with zero warnings |
| `guard.yml` → `publication-guard` | the shape check on the tree and on the new commits, identical generated proto copies with pinned generators, the three agent-signing trust stores identical, every cited `docs/*.md` exists, the licence map holds, no workflow runs untrusted code on a private runner, the configuration reference is current (`tools/configref`), the guard's own tests |
| `guard.yml` → `private-identifier-guard` | on push to `main` and in the merge queue only: the exact-list check from HMAC digests held in environment secrets; it is the required check that decides a merge |
| `security.yml` | `govulncheck` for the backend, agent and agent-signer modules and for the entitlement signer's `-tags piv` build (the signers with their smart-card headers) and `pnpm audit --prod` for the frontend; the backend and agent scans run through `tools/vulngate`, which lets a module's `accepted-<module>.txt` excuse a reachable advisory only with a written reason and a review date, and fails on an expired or a stale entry; scheduled as well as on push, because the advisory database moves while the code does not. |
| `platform-release.yml` | on a `platform-v*` tag: refuses a tag that is not a version or whose commit is not on `main`, then, behind the `release` environment, builds the server images natively per architecture, merges them into multi-architecture manifests tagged with the version, attests provenance, for a final release moves `latest` for all three images together, and creates the tag's GitHub Release (a pre-release for a release candidate; marked latest only for the highest final version), from which the installer takes its default version |

## The licence boundary

Two licences live in one tree, decided per directory
([`LICENSE`](LICENSE), [`REUSE.toml`](REUSE.toml)):

- Files in **`agent/`, `proto/` and every directory under `tools/`**, and
  the Apache-2.0 exceptions `REUSE.toml` lists, are distributed by Uptime
  Lab Inc. under the **Apache License 2.0** (the map is `REUSE.toml`'s,
  which wins over any copy of it).
- Files **anywhere else** (`backend/`, `frontend/`, `eeprom-signer/`,
  `docs/`, `postman/`, the root files) are distributed by Uptime Lab Inc.
  under the **Fair Core License 1.0, ALv2 Future License**.

Code may move from the Apache directories into the FCL ones freely. **Code is
moved from an FCL directory into an Apache directory only by the licensor**
(Uptime Lab Inc.); a pull request that copies server code into the agent
tree is declined on that ground alone, and `check_licence_boundary.py`
asserts the map in CI. If an agent-side change needs something the backend
already has, say so in the pull request and the maintainers will decide
whether to relicense that piece. The generated protocol code is Apache-2.0
wherever it is copied.

## Third-party material

Code, text, images or data you did not write yourself may be included only
under a licence on the accepted list below, or under another licence a
maintainer has approved in writing in the issue or pull request before the
merge.

- **Accepted**: MIT, BSD-2-Clause, BSD-3-Clause, ISC, Apache-2.0, Zlib,
  0BSD, BSL-1.0, CC0-1.0, and, for fonts shipped as separate files,
  OFL-1.1.
- **Ask in an issue first**: MPL-2.0 (the file stays under MPL-2.0 and
  cannot be relicensed), CC-BY-4.0 (documentation and images), the
  Unlicense and other public-domain dedications, and anything not listed
  here.
- **Not accepted**: GPL, LGPL and AGPL of any version, EUPL, SSPL, CC BY-SA
  (this includes code copied from answer sites published under it), any
  non-commercial or no-derivatives licence, other vendors' source-available
  licences (BUSL, FSL, FCL, the Elastic License), and anything with no
  licence stated.

For each third-party file, name it in the pull request description with
its source and licence, keep its copyright notice and licence header, add
an `[[annotations]]` entry for its path in `REUSE.toml` (the directory
defaults would otherwise label it wrongly), add its licence text under
`LICENSES/` and its notice to `THIRD-PARTY-NOTICES.md`. A dependency
fetched by a package manager needs none of this, but its licence must
still be on the list. `agent/`, `proto/` and `tools/` take Apache-2.0
third-party material only; CI refuses anything else there.

Code posted in an issue or a discussion is treated as a suggestion: it is
re-implemented, not copied.

## Contributor licence agreement

A pull request can be opened now. It is merged after the contributor licence
agreement is published and every human author of its commits has signed it;
until then it waits. For a typo or a small fix, open an issue saying what to
change and a maintainer will make the change.

Commits are public and stay in the history once merged, so commit under a
name and address you are content to publish (GitHub's no-reply address is
fine), and do not put anyone else's personal data in a contribution.
